# 기술 스택 결정 문서: 이지오더 (EasyOrder)

## 문서 정보
| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 |
| 기반 문서 | PRD / IA / 데이터 스키마 / 프로토타입 |
| 작성 단계 | 설계 (Design) → 구현(Build) 착수 전 |

---

## 1. 선택 기준 (요구사항에서 도출)

| 요구사항 (출처) | 기술적으로 필요한 것 |
|---|---|
| iOS/Android 둘 다 지원 (PRD 6) | 크로스플랫폼 프레임워크 |
| 브랜드/기계를 JSON 데이터로 관리, 앱 재배포 없이 갱신 (PRD 6.1, 스키마 문서) | 원격 콘텐츠 다운로드 + 로컬 캐시, 버전 비교 로직 |
| 오프라인에서도 저장된 가이드 열람 (PRD 6) | 로컬 DB/스토리지 |
| 음성 안내(TTS), 큰 글씨, 고대비 (PRD 6, IA 3장) | 플랫폼 TTS 연동, 시스템 폰트 크기 대응 |
| 빠른 MVP 검증 (서브웨이 1개 브랜드) | 개발 생산성이 높은 스택, 과한 인프라 지양 |
| 결제 데이터는 서버로 보내지 않음 (PRD, 스키마 4.6) | 결제 관련 백엔드 불필요 (모의 UI만) |

---

## 2. 클라이언트 프레임워크

| 후보 | 장점 | 단점 |
|---|---|---|
| **React Native (Expo)** | JS/JSX 하나로 iOS·Android 동시 대응, 프로토타입(React) 코드 자산 재사용 가능, TTS·로컬DB·OTA 업데이트 라이브러리 풍부, 빠른 MVP에 적합 | 고급 네이티브 UI 커스터마이징은 약간의 우회 필요 |
| Flutter | 성능 우수, UI 일관성 높음 | 프로토타입이 React 기반이라 처음부터 다시 작성해야 함, 학습 비용 |
| 완전 네이티브(Swift+Kotlin 각각) | 최고 성능·완전한 접근성 API 활용 | 두 배 인력/시간, MVP 단계에 과함 |

**결정: React Native(Expo)** — 지금까지 만든 프로토타입(React/JSX)의 컴포넌트 구조와 상태 로직을 거의 그대로 이어갈 수 있고, 콘텐츠(JSON) 기반으로 화면을 그리는 이 앱의 특성과 React의 선언적 렌더링 방식이 잘 맞음.

---

## 3. 상태 관리

- 전역 상태 라이브러리(Redux 등) 없이 **React Context + `useReducer`**로 시작
- 이유: 화면 흐름이 한 방향(홈→매장→모드→단계→완료)으로 단순하고, 상태도 `currentStep`, `selections`, `flow` 정도로 제한적 (IA 문서 4장 참고)
- 향후 기능이 복잡해지면(예: 여러 매장 동시 세션) 재검토

---

## 4. 로컬 저장

| 용도 | 기술 |
|---|---|
| 저장된 내 주문(SAVED_ORDER) | `expo-sqlite` 또는 `AsyncStorage`(MVP는 데이터량이 적어 AsyncStorage로 충분) |
| 다운로드한 브랜드 콘텐츠(ORDER_FLOW, DEVICE_PROFILE) 오프라인 캐시 | 파일시스템(`expo-file-system`)에 JSON 캐시 + `flow_version` 저장 |
| 접근성 설정(글씨 크기, 음성 on/off) | `AsyncStorage` |

---

## 5. 음성 안내 (TTS)

- `expo-speech` (iOS: AVSpeechSynthesizer, Android: TextToSpeech 래핑)
- 한국어 음성 엔진은 OS 기본 제공 음성을 사용 (별도 음성 파일 제작 불필요, 비용 절감)
- 추후 음성 품질 개선이 필요하면 클라우드 TTS(Google/Naver Clova 등) 검토

---

## 6. 콘텐츠 서버 (BRAND / ORDER_FLOW / DEVICE_PROFILE 배포)

**MVP 단계**: 별도 백엔드 서버 없이 **정적 JSON 파일 + CDN**으로 시작
- 예: JSON 파일을 클라우드 스토리지(Firebase Hosting, S3+CloudFront 등)에 올려두고, 앱이 실행 시 `flow_version`을 비교해 변경 시에만 다운로드
- 장점: 인프라 비용/운영 부담 최소화, 스키마 문서의 "앱 재배포 없이 콘텐츠 갱신" 요구를 그대로 만족

**브랜드가 늘어나는 시점(2단계 이후)**: 관리자가 JSON을 직접 편집하기 번거로워지면, 간단한 헤드리스 CMS(예: Strapi, 또는 Firebase 콘솔에 맞춘 자체 관리자 페이지) 도입 검토

---

## 7. 백엔드 / 사용자 데이터

- **MVP는 로그인 없이 전부 기기 로컬 저장** — 개인정보 최소 수집 원칙(PRD 6)에도 부합
- 추후 "보호자 연동 모드"(PRD 로드맵 4단계)처럼 기기 간 동기화가 필요해지면, 그때 Firebase/Supabase 같은 BaaS로 최소 범위(저장 주문만) 동기화 추가
- 결제는 앱이 처리하지 않으므로 PG 연동/결제 백엔드 불필요

---

## 8. 분석 (최소)

- PRD 2.3 KPI(주문 완료율, 재방문율 등) 측정을 위한 최소한의 이벤트 로깅만 추가
- Firebase Analytics 또는 Amplitude 중 택1 — 별도 대시보드 구축 없이 기본 제공 리포트로 MVP 검증에 충분

---

## 9. 배포

- Expo EAS Build로 iOS/Android 빌드 및 스토어 제출
- **Expo Updates(OTA)**로 코드 버그 수정은 스토어 심사 없이 신속 반영 (콘텐츠 JSON 갱신과는 별개 경로)
- 접근성 심사: 스토어 제출 전 iOS VoiceOver / Android TalkBack 기본 동작 확인

---

## 10. 접근성 관련 라이브러리/설정

- 시스템 폰트 크기 설정과 앱 내 "글씨 크기 조절"을 함께 대응 (`PixelRatio`, `useWindowDimensions` 활용)
- 터치 영역 최소 48x48pt는 컴포넌트 라이브러리 자체 제작 시 기본값으로 강제
- 색상 대비는 WCAG AA 기준으로 디자인 토큰 단계에서부터 체크

---

## 11. 리스크 및 대안

| 리스크 | 대응 |
|---|---|
| Expo의 특정 네이티브 기능 제약 | MVP 범위에서는 필요한 기능(TTS, 로컬 저장, 이미지 캐시)이 모두 Expo 지원 범위 내 — 문제 시 Expo의 "bare workflow"로 전환 가능 |
| AsyncStorage 성능 한계 | 저장 주문 수가 적어(개인 사용자 기준) MVP에서는 문제 없음. 데이터 늘면 SQLite로 전환 |
