# 콘텐츠 데이터 스키마 설계: 이지오더 (EasyOrder)

## 문서 정보
| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.2 (장바구니/카테고리-아이템 구조 개편, 7.4 참고) |
| 관련 원칙 | PRD 6.1 "확장 가능한 콘텐츠 아키텍처" 구체화 |
| 목적 | 브랜드/매장의 주문 단계를 앱 재배포 없이 서버 콘텐츠(JSON)로 관리하기 위한 데이터 구조 정의 |

---

## 1. 설계 원칙

1. **메뉴(MENU)는 브랜드 단위로 정의**한다. 같은 브랜드는 대부분 같은 카테고리/아이템 구성을 가지므로, 매장마다 반복 정의하지 않는다.
2. **매장별 예외가 필요할 경우에만** `STORE.menu_override_id`로 특정 메뉴를 덮어쓸 수 있게 한다 (MVP에서는 사용 안 함, 확장 여지만 확보).
3. **아이템 커스터마이징 단계(STEP)는 몇 가지 표준 유형(type)만 갖는다.** 새 브랜드를 추가해도 새로운 화면 컴포넌트를 개발하지 않고, 표준 유형 조합만으로 대부분의 흐름을 표현한다.
4. **주문은 장바구니(장바구니에 여러 아이템을 담아 한번에 결제) 단위로 진행**한다 (v1.2, 7.4 참고). 아이템별 커스터마이징은 그 아이템에만 스코프되고, 확인/결제는 장바구니 전체 단위로 진행한다.
5. **콘텐츠는 서버에서 버전 관리**하며, 앱은 시작 시 최신 버전을 확인해 다운로드/캐시한다. 앱스토어 심사 없이 콘텐츠 갱신이 가능해야 한다.

## 2. 엔티티 관계 (요약, v1.2)

```
BRAND (브랜드)
 ├─ STORE (매장)              — 브랜드에 속한 개별 지점
 ├─ MENU (메뉴)                — 브랜드의 표준 메뉴 구성
 │    └─ CATEGORY (카테고리, 예: 버거/음료)
 │         └─ ITEM (아이템, 예: 빅맥)
 │              └─ STEP (customize_steps, 이 아이템에만 스코프)
 │                   └─ OPTION (선택지)
 ├─ ORDER_STEPS (confirm/payment, 브랜드 전체 단위 — 장바구니를 대상으로 진행)
 └─ DEVICE_PROFILE (기계 형태) — 연습모드에서 재현할 실제 기계의 생김새

SAVED_ORDER (내 주문 저장)     — 특정 BRAND를 참조해 사용자가 장바구니(CART, 여러 라인)에 담은 값들을 기록
```

> 브랜드마다 실제로 쓰는 키오스크 기계 모양이 다르다 (예: 세로형 무인 키오스크, 카운터 위 태블릿형, 벽걸이형 등). 메뉴(MENU)를 데이터로 관리하는 것과 같은 원칙으로, **기계 모양(DEVICE_PROFILE)도 코드가 아니라 데이터로 관리**해서 새 브랜드 추가 시 앱이 알아서 알맞은 기계 모양을 그려주도록 한다.
>
> v1.0/v1.1에서는 "브랜드 단위 하나의 순차 흐름(ORDER_FLOW)"이었으나, v1.2(7.4)부터 "카테고리→아이템→아이템별 커스터마이징 + 장바구니"로 개편됐다.

## 3. 단계 유형 (Step Type) 표준 정의

| type | 설명 | 사용 예 (서브웨이) | 화면 컴포넌트 |
|---|---|---|---|
| `single_select` | 여러 선택지 중 정확히 1개만 선택 | 빵 종류, 굽기 여부 | 공통 단일선택 컴포넌트 |
| `multi_select` | 여러 선택지 중 0개 이상 선택 가능 | 야채, 소스, 사이드 | 공통 다중선택 컴포넌트 |
| `binary_choice` | 예/아니오 형태의 2지 선택 | "빵을 데워드릴까요?" | 공통 예/아니오 컴포넌트 |
| `payment_mock` | 결제 UI를 재현한 연습/안내 전용 단계 | 카드 삽입/페이 태그/영수증 여부 | 결제 연습 컴포넌트 (실결제 미처리) |
| `confirm` | 지금까지 선택한 내용 요약 확인 | 최종 주문 확인 | 공통 요약 컴포넌트 |

> 새 브랜드(예: 맥도날드) 추가 시, 이 5개 유형의 조합만으로 대부분의 흐름을 표현할 수 있어야 한다. 표현이 안 되는 유형이 발견되면 그때 새 표준 유형을 추가하고 문서를 갱신한다.

## 4. JSON 스키마 정의

### 4.1 BRAND
```json
{
  "brand_id": "string (unique)",
  "brand_name": "string",
  "logo_url": "string (optional)"
}
```

### 4.2 MENU (v1.2, 장바구니 구조로 개편 — 7.4 참고)

브랜드의 주문 흐름은 더 이상 "브랜드당 하나의 순차 단계열"이 아니라, **카테고리 → 아이템 → (아이템별) 커스터마이징 단계**로 구성되고, 사용자는 여러 아이템을 장바구니에 담았다가 한번에 결제한다.

```json
{
  "menu_id": "string (unique)",
  "categories": ["CATEGORY 배열"]
}
```

### 4.2.1 CATEGORY
```json
{
  "category_id": "string (unique within brand)",
  "label": "string (예: '버거', '음료')",
  "items": ["ITEM 배열"]
}
```

### 4.2.2 ITEM
```json
{
  "item_id": "string (unique across the whole brand — 카테고리 내 고유가 아님, 장바구니가 item_id만으로 참조)",
  "label": "string (예: '빅맥')",
  "base_price": "number",
  "visual": "one_of: bread | burger | drink | vegetable (optional)",
  "customize_steps": ["STEP 배열, 이 아이템에만 스코프됨 (빈 배열 가능 — 예: 단독 음료)"]
}
```

### 4.3 STEP (customize_steps 안에서 사용, 아이템 스코프)
```json
{
  "step_id": "string (unique within this item's customize_steps)",
  "type": "single_select | multi_select | binary_choice",
  "title": "string (화면 제목, 예: '빵 종류를 선택하세요')",
  "voice_text": "string (음성 안내 문구, title과 다를 수 있음)",
  "condition": "object, optional. {step_id, option_id} — 같은 아이템의 customize_steps 안의 다른 step_id만 참조 가능. 지정하면 그 단계에서 해당 옵션이 선택된 경우에만 이 단계를 노출. 없으면 항상 노출 (7.1, 7.4 참고). 여러 스텝이 같은 condition을 동시에 참조할 수 있음 (7.6 참고 — 예: 세트 선택 시 사이드+음료 둘 다 노출)",
  "max_selections": "int, optional. type이 multi_select일 때만 사용. 1 ≤ n ≤ options.length. 지정하면 그 개수까지만 선택 가능(캡 도달 시 추가 선택 무시, 해제는 항상 허용). 없으면 개수 제한 없음 (7.6 참고)",
  "options": ["OPTION 배열"]
}
```

`confirm`/`payment_mock` 타입은 더 이상 `customize_steps`에 쓰지 않고, 브랜드 전체에 하나씩 있는 `ORDER_STEPS`(4.3.1)로 옮겼다 — 장바구니 전체를 대상으로 하는 단계이기 때문이다.

### 4.3.1 ORDER_STEPS (브랜드 전체 단위, 장바구니 확인/결제)
```json
[
  { "step_id": "confirm_order", "type": "confirm", "title": "...", "voice_text": "..." },
  { "step_id": "payment", "type": "payment_mock", "title": "...", "voice_text": "...", "options": ["OPTION 배열, icon 필드 사용"] }
]
```
반드시 `confirm` 1개 다음 `payment_mock` 1개 순서로 정확히 2개 있어야 한다.

### 4.3.2 DINING_OPTIONS (브랜드 전체 단위, `menu`/`order_steps`와 형제, v1.3 신규)
```json
{
  "step_id": "dining",
  "type": "binary_choice",
  "title": "매장에서 드실 건가요, 포장하시겠어요?",
  "voice_text": "매장에서 드실지 포장하실지 선택해주세요.",
  "options": [
    { "option_id": "dine_in", "label": "매장에서 식사", "price": 0 },
    { "option_id": "takeaway", "label": "포장", "price": 0 }
  ]
}
```
`order_steps`에 넣지 않은 이유는 7.6 참고. 화면상으로는 매장 선택 직후, 카테고리 브라우징 시작 전에 노출된다.

### 4.4 OPTION
```json
{
  "option_id": "string (unique within step)",
  "label": "string (예: '화이트빵')",
  "price": "number (optional, 기본값 0)",
  "image_url": "string (optional)",
  "voice_text": "string (optional, 없으면 label 사용)"
}
```

### 4.5 DEVICE_PROFILE (기계 형태)
```json
{
  "device_id": "string (unique)",
  "brand_id": "string (FK -> BRAND)",
  "shape": "freestanding_totem | countertop_tablet | wall_mounted",
  "orientation": "portrait | landscape",
  "bezel_color": "string (hex)",
  "notes": "string (optional, 운영자용 메모, 예: '2024년형 모델 기준')"
}
```

| shape | 설명 | 예시 브랜드 |
|---|---|---|
| `freestanding_totem` | 세로로 긴 거치대 + 상단 화면 (일반적인 무인 키오스크) | 서브웨이 |
| `countertop_tablet` | 카운터 위에 놓인 작은 태블릿형 화면 | 버거킹(예시) |
| `wall_mounted` | 벽이나 카운터 상단에 고정된 화면 | (추후 확장) |

> `shape` 값은 표준 유형으로 제한한다 (STEP의 `type`과 같은 원칙). 새 브랜드 추가 시 이미 정의된 3가지 형태 중 하나를 고르면 되고, 정말 새로운 형태가 필요할 때만 표준 목록에 추가한다. 화면 안의 내용(빵 사진 타일 등)은 ORDER_FLOW/STEP/OPTION 데이터를 그대로 재사용하므로 기계 모양과 무관하게 동일한 로직으로 렌더링된다.

### 4.6 SAVED_ORDER (내 주문 저장, 로컬 우선, v1.2 장바구니 구조로 개편)
```json
{
  "saved_order_id": "string (unique, 로컬 생성)",
  "brand_id": "string (FK -> BRAND)",
  "nickname": "string (사용자가 지정, 예: '내가 좋아하는 조합')",
  "cart": [
    {
      "cartItemId": "string (unique, 로컬 생성)",
      "categoryId": "string (FK -> CATEGORY)",
      "itemId": "string (FK -> ITEM)",
      "label": "string (담을 때 아이템 이름 스냅샷)",
      "customizeSelections": { "step_id_1": ["option_id"] },
      "optionLabels": ["string, 선택한 옵션 라벨 목록 (요약 표시용)"],
      "unitPrice": "number",
      "qty": "number",
      "lineTotal": "number (unitPrice * qty)"
    }
  ],
  "created_at": "ISO8601 datetime"
}
```

## 5. 서브웨이 예시 전체 데이터 (축약, v1.2 스키마 기준 — 실제 `content-pipeline/brands/subway.json`과 동일)

                "step_id": "bread",
                "type": "single_select",
                "title": "빵 종류를 선택하세요",
                "voice_text": "먼저 빵 종류를 골라주세요.",
                "options": [
                  { "option_id": "white", "label": "화이트빵" },
                  { "option_id": "wheat", "label": "위트빵" },
                  { "option_id": "italian", "label": "이탈리안 빵" }
                ]
              },
              {
                "step_id": "toast",
                "type": "binary_choice",
                "title": "빵을 데워드릴까요?",
                "voice_text": "빵을 따뜻하게 데워드릴지 선택해주세요.",
                "options": [
                  { "option_id": "yes", "label": "네, 데워주세요" },
                  { "option_id": "no", "label": "아니요" }

              },
              {
                "step_id": "vegetables",
                "type": "multi_select",
                "title": "야채를 선택하세요",

                  { "option_id": "lettuce", "label": "양상추" },

      "step_id": "confirm_order",
      "type": "confirm",
      "title": "선택하신 내용을 확인해주세요",

      "type": "payment_mock",
      "title": "결제 방법을 선택하세요",

        { "option_id": "phone", "label": "휴대폰 태그", "icon": "phone" },

> `order_steps`(confirm/payment)는 모든 브랜드가 동일한 2개 표준 유형을 재사용한다. 브랜드마다 다른 것은 `menu.categories`의 내용(카테고리·아이템이 몇 개인지, 각 아이템의 `customize_steps`가 무엇인지)뿐이다. 맥도날드처럼 카테고리가 여러 개(버거+음료)이고 아이템마다 조건부 단계가 있는 경우는 4.2~4.3, 7.4를 참고.

## 5.1 기계 형태(DEVICE_PROFILE) 예시

```json
[
  {
    "device_id": "subway_totem_v1",
    "brand_id": "subway",
    "shape": "freestanding_totem",
    "orientation": "portrait",
    "bezel_color": "#33372F"
  },
  {
    "device_id": "burgerking_tablet_v1",
    "brand_id": "burgerking",
    "shape": "countertop_tablet",
    "orientation": "landscape",
    "bezel_color": "#B9BDB6"
  }
]
```

두 브랜드는 메뉴 구성도 다르고(서브웨이는 카테고리 1개·아이템 1개의 빌드유어오운, 버거킹은 카테고리 1개·아이템 3개), `DEVICE_PROFILE`의 기계 모양도 다르다. 앱은 두 데이터를 각각 읽어서, 코드 수정 없이 서로 다른 기계 모양 + 서로 다른 메뉴 구성을 동시에 지원한다.

## 6. 콘텐츠 업데이트 / 신규 브랜드 추가 운영 흐름

1. 매장의 실제 키오스크 UI 변경 확인 (운영팀 또는 제보)
2. 위 JSON 스키마에 맞춰 `menu_id`(또는 필요 시 별도 버전 필드)를 올려 새 콘텐츠 작성
3. 콘텐츠 서버(추후 CMS 또는 관리자 도구)에 업로드
4. 앱은 실행 시 메뉴 버전을 서버와 비교 → 변경 시 최신 콘텐츠 다운로드 및 로컬 캐시 갱신
5. 앱스토어 심사/재배포 없이 콘텐츠만으로 반영 완료

**신규 브랜드(예: 맥도날드) 추가 시**:
- `BRAND` 레코드 1개 추가
- 해당 브랜드의 `MENU` + `CATEGORY` + `ITEM` + `STEP`(customize_steps) + `OPTION` 데이터 작성 (개발자 코드 수정 불필요, 표준 유형 조합으로 작성)
- 홈 화면(S02)의 브랜드 목록에 자동 노출 (브랜드 목록도 서버 콘텐츠로 관리)

## 7. 알려진 제약사항 및 개선 이력

### 7.1 조건부 단계(분기) — ✅ 해결 (v1.1)

**발견 경위**: 맥도날드 콘텐츠를 채우는 과정에서 발견. 맥도날드·롯데리아·KFC 3개 브랜드 모두 "세트로 선택했을 때만 음료 선택 화면이 나오고, 단품이면 생략"되는 조건부 흐름을 써서, 우연히 하나가 아니라 반복되는 패턴임이 확인됐다. 처음엔 STEP이 항상 순서대로만 진행되는 선형 구조라 이 분기를 표현할 수 없어 "음료 단계를 항상 보여주되 안내 문구로 눈속임"하는 임시 대응을 했는데, 브랜드 3곳에 동시 적용해보니 **단품을 선택해도 음료 단계가 나오고, 주문확인 화면에 안 고른 음료가 뜨고, 심지어 가격 합계에도 잘못 더해지는 실제 버그**로 드러났다.

**해결책**: STEP에 `condition` 필드를 추가했다.

```json
{
  "step_id": "drink",
  "type": "single_select",
  "condition": { "step_id": "set", "option_id": "set" },
  "...": "..."
}
```

- `condition.step_id`: 같은 flow 안의 다른 step_id를 참조
- `condition.option_id`: 그 step에서 이 option_id가 선택되어 있어야만 현재 단계를 노출
- `condition`이 없으면 항상 노출 (기존 동작과 100% 호환)

**적용 범위**: mcdonalds.json, lotteria.json, kfc.json의 `drink` 단계에 `condition: {step_id: "set", option_id: "set"}` 적용 — "세트"를 선택했을 때만 음료 단계가 나타나고, "단품"을 선택하면 건너뛴다.

**검증**: 당시엔 `content-pipeline/tests/conditional-steps.test.js`로 자동 테스트했다 (섹션 7.2 참고). v1.2(7.4)에서 스키마가 아이템 스코프로 바뀌면서 이 파일은 `content-pipeline/tests/cart.test.js`로 대체됐다 — 같은 회귀 시나리오를 포함해서 이어가고 있다.

> ⚠️ 이 섹션의 `condition.step_id`가 "같은 flow 안의 다른 step_id"를 참조한다는 설명은 v1.1 당시 기준이다. v1.2(7.4)부터는 "같은 아이템의 customize_steps 안"으로 스코프가 좁혀졌다 — 4.3 참고.

### 7.2 자동 테스트 (v1.1 당시 기록)

콘텐츠 파일이 늘어나도 조건부 단계 로직이 깨지지 않는지 확인하기 위해 `content-pipeline/tests/conditional-steps.test.js`를 추가했다. 브랜드 JSON을 직접 읽어 시나리오별(세트 선택 / 단품 선택)로 노출 단계와 합계 금액을 검증했다. v1.2부터는 `content-pipeline/tests/cart.test.js`(`node tests/cart.test.js`)가 이 역할을 이어받는다 — 7.4 참고.

### 7.3 사이드 메뉴 단순화

맥도날드 세트의 사이드(감자튀김)는 실제로는 별도 선택 단계가 있지만, mcdonalds.json에서는 "기본 감자튀김(M) 고정"으로 단순화했다. 사이드 선택까지 반영할지는 조사 대상이 늘어난 뒤 필요성을 재검토한다.

### 7.4 장바구니(카트) 구조로 전면 개편 (v1.2)

**발견 경위**: 실사용 관점에서 검토하면서 세 가지 문제가 드러났다. (1) 매장을 먼저 고르고 모드(연습/실시간)를 나중에 고르는 순서가 부자연스러움, (2) 7.1에서 해결한 `condition` 기반 "세트여야만 음료 노출" 로직이 실제로는 "단품이어도 음료를 따로 살 수 있어야 한다"는 요구를 막고 있었음(메뉴 옵션이 적어서 생긴 임시방편), (3) 메뉴 하나 고르면 바로 결제로 넘어가는 단일 흐름이라 여러 메뉴를 한번에 주문할 수 없었음.

**해결책**: 브랜드당 하나의 순차 `flow.steps` 배열을 **`menu.categories[].items[].customize_steps[]` + 브랜드 전체 단위 `order_steps`**로 교체하고(4.2~4.4 참고), 사용자가 여러 아이템을 장바구니(`cart`, 4.6 참고)에 담아 한번에 결제하는 흐름으로 바꿨다. `condition` 필드는 폐기하지 않고 **아이템 스코프로 좁혔다** — 예: 맥도날드 버거 아이템 안에서 "세트" 선택 시에만 그 아이템에 포함된 무료 음료 선택 단계가 나타나는 것은 그대로 유지하되, 이제는 음료를 그 버거의 세트와 무관하게 **별도 `drinks` 카테고리에서 독립적으로 장바구니에 추가**할 수도 있다. 즉 "세트 포함 음료(무료)"와 "단독 구매 음료(유료)" 두 경로가 공존한다.

**네비게이션도 함께 바뀌었다**: 홈(모드 선택) → 매장 선택 → 카테고리/아이템 브라우징 → 아이템 커스터마이징 → 장바구니 확인 → 결제 → 완료. 매장 선택이 모드 선택보다 뒤로 이동했다.

**적용 범위**: 5개 브랜드 전부 새 스키마로 마이그레이션. 맥도날드·롯데리아·KFC는 기존 `drink` 옵션을 `drinks` 카테고리로 추출(실질적 콘텐츠 확장). 서브웨이·버거킹은 최초엔 기존 아이템/커스터마이징을 그대로 새 스키마 모양으로만 옮겼고(메뉴 개수 확장은 그 시점 범위에서 제외), 실제 확장은 7.5에서 곧바로 이어졌다.

**검증**: `content-pipeline/tests/conditional-steps.test.js`를 `content-pipeline/tests/cart.test.js`로 교체 — 장바구니 총액 계산, 동일 아이템 병합(qty), 다른 옵션이면 별도 라인 유지, 라인 삭제, 아이템 스코프 조건부(7.1의 회귀 테스트 포함) 등 44개 시나리오로 확장.

### 7.5 서브웨이/버거킹 메뉴 확장

7.4에서 범위 제외했던 서브웨이·버거킹 메뉴 개수 확장을 곧바로 진행했다.

- **서브웨이**: 고정 아이템 1개(`default_sub`) → 실제 샌드위치 6종(에그마요/참치/미트볼 마리나라/터키 브레스트/이탈리안 비엠티/서브웨이 클럽)으로 확장. 스키마 설계 문서(§5, v1.0 초안)에는 있었지만 구현되지 않았던 **소스 선택 단계**를 각 아이템의 `customize_steps`에 추가(스위트어니언/마요네즈/허니 머스타드). `drinks` 카테고리 신설.
- **버거킹**: 기존 3종(와퍼/치즈버거/치킨버거)에 3종(통새우와퍼/불고기와퍼/와퍼주니어) 추가. 다른 4개 브랜드와 동일하게 **세트 선택 시 무료 음료 포함 단계(`included_drink`, `condition` 기반)**를 6종 전체에 추가 — 이전까지는 버거킹만 이 패턴이 없었다. `drinks` 카테고리 신설.
- **테스트 영향**: `cart.test.js`의 "condition 없는 브랜드" 검증 그룹을 서브웨이 단독으로 좁히고, 버거킹은 맥도날드·롯데리아·KFC와 같은 조건부 검증 그룹으로 이동(57개 시나리오로 확장). `src/App.jsx`의 하드코딩된 `CONTENT` 객체(콘텐츠 파이프라인 JSON의 임시 복사본)도 동일하게 갱신 — `mobile/`은 JSON을 직접 import하므로 별도 수정 불필요했다.
- **가격 출처**: 서브웨이 6종/버거킹 3종 신규 가격은 각 브랜드 대표 메뉴 가격대를 참고한 추정치로, 두 파일의 `_source_notes`에 명시. 현장/공식 채널 확인 전까지는 잠정치.

### 7.6 실제 키오스크 프로세스 정합성 개선 (v1.3)

**발견 경위**: 5개 브랜드의 주문 흐름이 실제 매장 키오스크 운영 프로세스와 얼마나 일치하는지 공식 사이트(subway.co.kr, mcdonalds.co.kr 등)와 나무위키를 직접 조사해서 검토했다. 서브웨이는 실제 9단계(메뉴→빵→빵길이→치즈→추가토핑(유료)→토스팅→야채→소스→세트) 중 4단계만 구현돼 있었고 세트 옵션 자체가 없었다. KFC는 실제로 "치킨&세트"/"버거&세트"가 분리된 카테고리이고 치킨은 조각 단위로 맛을 섞어("반반") 주문하는 게 정체성인데, 지금까지는 다른 버거 브랜드와 완전히 동일한 패턴(버거+세트토글)으로만 구현돼 있었다. 버거킹/맥도날드/롯데리아는 세트 시 사이드·음료 교체나 사이즈 업그레이드가 실제로 있는데 지금까지는 간소화돼 있었다. 공통으로는 매장식사/포장 여부를 첫 화면에서 묻는 실제 키오스크 관행이 빠져 있었고, `order_steps`의 `confirm_order` 텍스트가 화면 코드에서 전혀 읽히지 않는 죽은 데이터였다.

**스키마 변경**:

1. **`max_selections`(신규, `multi_select` 스텝 전용 선택적 필드)** — 서브웨이 소스처럼 "최대 N개까지" 제한이 있는 경우에 사용. `1 ≤ max_selections ≤ options.length`. 초과 선택 시 유료화 같은 복잡한 로직 없이 단순히 선택이 막힘(이미 선택된 항목은 해제 가능). 우선 UI가 캡을 강제하고, 선택 로직(`toggleCustomizeOption`)에서도 캡 도달 시 신규 선택을 무시하도록 방어.

2. **`dining_options`(신규 최상위 필드, `menu`/`order_steps`와 형제)** — 매장식사/포장 여부. `order_steps`에 넣지 않은 이유: `order_steps`는 "confirm 1개 + payment_mock 1개, 정확히 2개"로 고정 검증되고 의미상 "장바구니 확인/결제"를 뜻하는데, 매장식사/포장은 메뉴 브라우징 시작 **전**에 묻는 질문이라 이 배열에 넣으면 순서·의미가 어긋난다. 형태:
   ```jsonc
   "dining_options": {
     "step_id": "dining", "type": "binary_choice",
     "title": "매장에서 드실 건가요, 포장하시겠어요?", "voice_text": "...",
     "options": [{ "option_id": "dine_in", "label": "매장에서 식사", "price": 0 }, { "option_id": "takeaway", "label": "포장", "price": 0 }]
   }
   ```
   화면상으로는 매장 선택 직후, 카테고리 브라우징 시작 전에 새 화면(`'diningOption'`)으로 끼워넣었다.

3. **`confirm_order` 데이터 연결(wiring)** — 5개 브랜드 JSON `order_steps`에 처음부터 있었던 `confirm_order`(title/voice_text)가 실제로는 장바구니 확인 화면 코드에서 읽히지 않고 화면 자체의 하드코딩된 문구("장바구니")를 쓰고 있었다. 스키마를 삭제하는 대신(더 파괴적) 화면 코드가 이 데이터를 실제로 읽도록 연결했다 — 근본 원인을 고치는 쪽을 선택.

4. **조건부 스텝 다중 참조** — `included_side`와 `included_drink` 둘 다 같은 `condition: {step_id:"set", option_id:"set"}`을 참조하는 경우(버거킹의 세트 시 사이드+음료 둘 다 교체 가능), 검증기(`validate.js`)의 `stepById` 조회 로직은 원래부터 단일 소비자 제약이 없어서 **스키마/검증기 변경 없이 그대로 동작**한다.

5. **세트 사이즈 업그레이드(`set_size`)** — 새 스텝 타입 없이 기존 `binary_choice`를 조건부(`{set,set}`)로 하나 더 추가하는 패턴으로 처리(맥도날드 L세트, 버거킹 라지 업그레이드).

6. **KFC 치킨 조각/맛 조합** — "조각별로 다른 맛을 섞어 주문"하는 실제 주문 방식을 정확히 모델링하려면 조각 단위 배정이 필요하지만, 이 앱의 목적(키오스크 버튼 누르는 법 연습)에는 과합하다고 판단해 **버킷을 하나의 아이템으로, 맛 선택을 `multi_select`+`max_selections:2` 스텝 하나로 근사**했다 — 1개 선택=그 맛 전체, 2개 선택="반반" 구성으로 간주. 새 스텝 타입이나 N조각-N맛 매트릭스 같은 일반화된 구조는 만들지 않았다.

**PHASES 문구 통일**: 웹(`'장바구니'`)과 모바일(`'주문확인'`)이 서로 다르게 구현되어 있던 걸 발견 — 실제 키오스크 용어(조사 결과 롯데리아의 "주문 내역과 총 금액 확인")에 가깝게 **"주문확인"**으로 통일했다. 모바일 쪽에는 아무도 참조하지 않는 중복 `PHASES` export도 있었는데 제거했다.

**적용 범위**: 서브웨이 전면 리작업(9단계, 야채 9종/소스 15종으로 확장), KFC 전면 재설계(치킨 카테고리 신설, 기존 버거는 유지), 버거킹(세트 사이드+음료 교체, 라지 업그레이드), 맥도날드(세트 사이즈 업그레이드, 맥모닝/사이드&디저트/맥카페 카테고리 신설), 롯데리아(세트 사이드 교체, 치킨 카테고리 신설), 공통(다이닝옵션 화면, confirm_order 연결).

**검증**: `content-pipeline/tests/cart.test.js`에 max_selections 캡, KFC 맛조합, 다중조건부 게이팅, dining_options 구조 등 신규 시나리오 추가.
