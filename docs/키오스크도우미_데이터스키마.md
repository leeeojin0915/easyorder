# 콘텐츠 데이터 스키마 설계: 이지오더 (EasyOrder)

## 문서 정보
| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 |
| 관련 원칙 | PRD 6.1 "확장 가능한 콘텐츠 아키텍처" 구체화 |
| 목적 | 브랜드/매장의 주문 단계를 앱 재배포 없이 서버 콘텐츠(JSON)로 관리하기 위한 데이터 구조 정의 |

---

## 1. 설계 원칙

1. **주문 흐름(ORDER_FLOW)은 브랜드 단위로 정의**한다. 같은 브랜드는 대부분 같은 주문 절차를 가지므로, 매장마다 반복 정의하지 않는다.
2. **매장별 예외가 필요할 경우에만** `STORE.flow_override_id`로 특정 흐름을 덮어쓸 수 있게 한다 (MVP에서는 사용 안 함, 확장 여지만 확보).
3. **단계(STEP)는 몇 가지 표준 유형(type)만 갖는다.** 새 브랜드를 추가해도 새로운 화면 컴포넌트를 개발하지 않고, 표준 유형 조합만으로 대부분의 흐름을 표현한다.
4. **콘텐츠는 서버에서 버전 관리**하며, 앱은 시작 시 최신 버전을 확인해 다운로드/캐시한다. 앱스토어 심사 없이 콘텐츠 갱신이 가능해야 한다.

---

## 2. 엔티티 관계 (요약)

```
BRAND (브랜드)
 ├─ STORE (매장)              — 브랜드에 속한 개별 지점
 ├─ ORDER_FLOW (주문 흐름)     — 브랜드의 표준 주문 절차
 │    └─ STEP (단계, 순서 있음)
 │         └─ OPTION (선택지)
 └─ DEVICE_PROFILE (기계 형태) — 연습모드에서 재현할 실제 기계의 생김새

SAVED_ORDER (내 주문 저장)     — 특정 ORDER_FLOW를 참조해 사용자가 선택한 값들을 기록
```

> 브랜드마다 실제로 쓰는 키오스크 기계 모양이 다르다 (예: 세로형 무인 키오스크, 카운터 위 태블릿형, 벽걸이형 등). 주문 절차(ORDER_FLOW)를 데이터로 관리하는 것과 같은 원칙으로, **기계 모양(DEVICE_PROFILE)도 코드가 아니라 데이터로 관리**해서 새 브랜드 추가 시 앱이 알아서 알맞은 기계 모양을 그려주도록 한다.

---

## 3. 단계 유형 (Step Type) 표준 정의

| type | 설명 | 사용 예 (서브웨이) | 화면 컴포넌트 |
|---|---|---|---|
| `single_select` | 여러 선택지 중 정확히 1개만 선택 | 빵 종류, 굽기 여부 | 공통 단일선택 컴포넌트 |
| `multi_select` | 여러 선택지 중 0개 이상 선택 가능 | 야채, 소스, 사이드 | 공통 다중선택 컴포넌트 |
| `binary_choice` | 예/아니오 형태의 2지 선택 | "빵을 데워드릴까요?" | 공통 예/아니오 컴포넌트 |
| `payment_mock` | 결제 UI를 재현한 연습/안내 전용 단계 | 카드 삽입/페이 태그/영수증 여부 | 결제 연습 컴포넌트 (실결제 미처리) |
| `confirm` | 지금까지 선택한 내용 요약 확인 | 최종 주문 확인 | 공통 요약 컴포넌트 |

> 새 브랜드(예: 맥도날드) 추가 시, 이 5개 유형의 조합만으로 대부분의 흐름을 표현할 수 있어야 한다. 표현이 안 되는 유형이 발견되면 그때 새 표준 유형을 추가하고 문서를 갱신한다.

## 4. JSON 스키마 정의

### 4.1 BRAND
```json
{
  "brand_id": "string (unique)",
  "brand_name": "string",
  "logo_url": "string (optional)"
}
```

### 4.2 ORDER_FLOW
```json
{
  "flow_id": "string (unique)",
  "brand_id": "string (FK -> BRAND)",
  "flow_version": "string (semver, e.g. 1.0.0)",
  "updated_at": "ISO8601 datetime",
  "steps": ["STEP 배열, order 순으로 정렬"]
}
```

### 4.3 STEP
```json
{
  "step_id": "string (unique within flow)",
  "order": "int",
  "type": "single_select | multi_select | binary_choice | payment_mock | confirm",
  "title": "string (화면 제목, 예: '빵 종류를 선택하세요')",
  "voice_text": "string (음성 안내 문구, title과 다를 수 있음)",
  "condition": "object, optional. {step_id, option_id} — 지정하면 그 이전 단계에서 해당 옵션이 선택된 경우에만 이 단계를 노출. 없으면 항상 노출 (7.1 참고)",
  "options": ["OPTION 배열 (payment_mock, confirm 타입은 별도 구조 사용)"]
}
```

### 4.4 OPTION
```json
{
  "option_id": "string (unique within step)",
  "label": "string (예: '화이트빵')",
  "image_url": "string (optional)",
  "voice_text": "string (optional, 없으면 label 사용)"
}
```

### 4.5 DEVICE_PROFILE (기계 형태)
```json
{
  "device_id": "string (unique)",
  "brand_id": "string (FK -> BRAND)",
  "shape": "freestanding_totem | countertop_tablet | wall_mounted",
  "orientation": "portrait | landscape",
  "bezel_color": "string (hex)",
  "notes": "string (optional, 운영자용 메모, 예: '2024년형 모델 기준')"
}
```

| shape | 설명 | 예시 브랜드 |
|---|---|---|
| `freestanding_totem` | 세로로 긴 거치대 + 상단 화면 (일반적인 무인 키오스크) | 서브웨이 |
| `countertop_tablet` | 카운터 위에 놓인 작은 태블릿형 화면 | 버거킹(예시) |
| `wall_mounted` | 벽이나 카운터 상단에 고정된 화면 | (추후 확장) |

> `shape` 값은 표준 유형으로 제한한다 (STEP의 `type`과 같은 원칙). 새 브랜드 추가 시 이미 정의된 3가지 형태 중 하나를 고르면 되고, 정말 새로운 형태가 필요할 때만 표준 목록에 추가한다. 화면 안의 내용(빵 사진 타일 등)은 ORDER_FLOW/STEP/OPTION 데이터를 그대로 재사용하므로 기계 모양과 무관하게 동일한 로직으로 렌더링된다.

### 4.6 SAVED_ORDER (내 주문 저장, 로컬 우선)
```json
{
  "saved_order_id": "string (unique, 로컬 생성)",
  "flow_id": "string (FK -> ORDER_FLOW)",
  "brand_id": "string (FK -> BRAND)",
  "nickname": "string (사용자가 지정, 예: '내가 좋아하는 조합')",
  "selections": {
    "step_id_1": ["option_id"],
    "step_id_2": ["option_id_a", "option_id_b"]
  },
  "created_at": "ISO8601 datetime"
}
```

```json
[
  {
    "device_id": "subway_totem_v1",
    "brand_id": "subway",
    "shape": "freestanding_totem",
    "orientation": "portrait",
    "bezel_color": "#33372F"
  },
  {
    "device_id": "burgerking_tablet_v1",
    "brand_id": "burgerking",
    "shape": "countertop_tablet",
    "orientation": "landscape",
    "bezel_color": "#B9BDB6"
  }

```

두 브랜드는 `ORDER_FLOW`의 단계 구성도 다르고(서브웨이는 빵→야채→결제, 버거킹은 메뉴→구성→결제), `DEVICE_PROFILE`의 기계 모양도 다르다. 앱은 두 데이터를 각각 읽어서, 코드 수정 없이 서로 다른 기계 모양 + 서로 다른 주문 절차를 동시에 지원한다.

## 6. 콘텐츠 업데이트 / 신규 브랜드 추가 운영 흐름

1. 매장의 실제 키오스크 UI 변경 확인 (운영팀 또는 제보)
2. 위 JSON 스키마에 맞춰 `flow_version`을 올려 새 콘텐츠 작성
3. 콘텐츠 서버(추후 CMS 또는 관리자 도구)에 업로드
4. 앱은 실행 시 `flow_version`을 서버와 비교 → 변경 시 최신 콘텐츠 다운로드 및 로컬 캐시 갱신
5. 앱스토어 심사/재배포 없이 콘텐츠만으로 반영 완료

**신규 브랜드(예: 맥도날드) 추가 시**:
- `BRAND` 레코드 1개 추가
- 해당 브랜드의 `ORDER_FLOW` + `STEP` + `OPTION` 데이터 작성 (개발자 코드 수정 불필요, 5개 표준 유형 조합으로 작성)
- 홈 화면(S02)의 브랜드 목록에 자동 노출 (브랜드 목록도 서버 콘텐츠로 관리)

## 7. 알려진 제약사항 및 개선 이력

### 7.1 조건부 단계(분기) — ✅ 해결 (v1.1)

**발견 경위**: 맥도날드 콘텐츠를 채우는 과정에서 발견. 맥도날드·롯데리아·KFC 3개 브랜드 모두 "세트로 선택했을 때만 음료 선택 화면이 나오고, 단품이면 생략"되는 조건부 흐름을 써서, 우연히 하나가 아니라 반복되는 패턴임이 확인됐다. 처음엔 STEP이 항상 순서대로만 진행되는 선형 구조라 이 분기를 표현할 수 없어 "음료 단계를 항상 보여주되 안내 문구로 눈속임"하는 임시 대응을 했는데, 브랜드 3곳에 동시 적용해보니 **단품을 선택해도 음료 단계가 나오고, 주문확인 화면에 안 고른 음료가 뜨고, 심지어 가격 합계에도 잘못 더해지는 실제 버그**로 드러났다.

**해결책**: STEP에 `condition` 필드를 추가했다.

```json
{
  "step_id": "drink",
  "type": "single_select",
  "condition": { "step_id": "set", "option_id": "set" },
  "...": "..."
}
```

- `condition.step_id`: 같은 flow 안의 다른 step_id를 참조
- `condition.option_id`: 그 step에서 이 option_id가 선택되어 있어야만 현재 단계를 노출
- `condition`이 없으면 항상 노출 (기존 동작과 100% 호환)

**적용 범위**: mcdonalds.json, lotteria.json, kfc.json의 `drink` 단계에 `condition: {step_id: "set", option_id: "set"}` 적용 — "세트"를 선택했을 때만 음료 단계가 나타나고, "단품"을 선택하면 건너뛴다.

**검증**: `content-pipeline/tests/conditional-steps.test.js`로 자동 테스트 (섹션 7.2 참고).

### 7.2 자동 테스트

콘텐츠 파일이 늘어나도 조건부 단계 로직이 깨지지 않는지 확인하기 위해 `content-pipeline/tests/conditional-steps.test.js`를 추가했다. 브랜드 JSON을 직접 읽어 시나리오별(세트 선택 / 단품 선택)로 노출 단계와 합계 금액을 검증한다. `node tests/conditional-steps.test.js`로 실행.

### 7.3 사이드 메뉴 단순화

맥도날드 세트의 사이드(감자튀김)는 실제로는 별도 선택 단계가 있지만, mcdonalds.json에서는 "기본 감자튀김(M) 고정"으로 단순화했다. 사이드 선택까지 반영할지는 조사 대상이 늘어난 뒤 필요성을 재검토한다.
